= Making Content for {OR}

About ORTS:: Open Rails Train Simulator is an open-source simulator created after Microsoft Train Simulator 2.0 was cancelled. {OR} is designed to remain compatible with most existing {MSTS} content while adding new features and fixing many old Microsoft/Kuju limitations. MSTS and ORTS terms are often used interchangeably, but {OR} can handle more complex models, higher polygon counts, longer viewing distances, 32-bit color, and many simulator features that {MSTS} does not support.

(((Open Rails, "The Open Rails Train Simulator, free and open source project" )))

OPEN RAILS::
Compared with Microsoft Train Simulator, Open Rails can usually keep good frame rates with more polygons. This allows smoother curves and more modeled detail. Open Rails also supports 32-bit color, while Microsoft Train Simulator is limited to 16-bit color. View distance can also be adjusted from about 2 km to 10 km.

_from Open Rails.org website_

This notebook focuses on using Blender. Other 3D modeling tools are mentioned only when they provide useful contrast.

== Common Terms and Definitions
(((Making Contentm TERMS. DEFINITIONS)))

3D modeling and simulator content creation use specialized terms. The following definitions cover the terms used most often in this notebook.

ALPHA:: A bitmap channel that makes part of an image transparent or partially transparent.
DISTANCE LEVELS:: See Level of Detail (LOD).
EDGE:: A line connecting two vertices.
ENG FILE:: A simulator configuration file for an engine or locomotive. It defines physical details such as motive power, braking, couplers, and other properties.
FACE:: A surface made from three or more vertices.
FOOBIE:: A deliberately low-detail model that uses texture detail to create many visual variants from one base shape. The term is a contraction of "fake boobies."
HARD SURFACE MODELING:: Modeling rigid objects such as vehicles, buildings, weapons, roads, and machinery. It usually uses standard mesh objects such as cubes, cylinders, planes, cones, and torus shapes.
HDRI:: High Dynamic Range Image. In Blender, HDRI environment maps are often used to light a scene with realistic real-world lighting information.
HIERARCHY:: The parent-child relationship between objects in a shape. Child objects can move on their own, but they are still affected by the parent object.
LEVEL OF DETAIL:: (LOD) A system that swaps the main model for simpler versions at greater distances. Distant models need fewer details because the viewer cannot see them clearly. There are no fixed LOD ranges, but you should use them when they help performance.
MANIFOLD SHAPE:: A watertight 3D object. Its vertices, edges, and faces connect so that no water would leak out if the object were filled. A default cube is manifold.
MATERIAL:: A surface definition assigned to a model. It may include a texture, lighting behavior, palette information, and shading settings.
MESH:: A 3D model shape made from faces, before textures are applied.
NGON:: A face with five or more vertices. Many Blender tools work best with quads or ngons and may not work as well after a mesh has been triangulated.
NORMAL:: A vector perpendicular to a face. Normals control which way a face points and affect how textures and lighting are displayed. footnote:[See https://en.wikipedia.org/wiki/Normal_(geometry)]
OBJECT:: A 2D object has length and height but no depth, such as a plane, polygon, or line. A 3D object has length, height, and depth, such as a cube or sphere.
ORGANIC MODELING:: Sculpted modeling for subjects such as people, animals, plants, trees, and some vehicles. Blender includes sculpting tools and NURBS-related tools, but those workflows are outside the scope of this notebook.
ORIGIN:: See Pivot Point.
PIVOT POINT:: The position used to align, rotate, and place a shape. It is also called the object's origin.
POLY COUNT:: The total number of polygons used in a mesh. It is a common way to describe model complexity.
POLYGON:: A flat face of a mesh. Edges define the polygon boundary, and vertices are the points where the edges meet. Blender commonly refers to triangle faces as tris and four-vertex faces as quads.
QUAD:: A face made from four vertices.
SHAPE:: A finished 3D object that is ready to be placed in the simulator environment.
SMOOTHING:: A shading setting that controls how individual polygons are lit by the simulator.
TRI:: A face made from three vertices. Also called a triangle.
UV:: The mapping system that projects a 2D texture image onto a 3D model. U and V are the texture axes, while X, Y, and Z are already used for 3D space.
VERTEX:: A point in 3D space with X, Y, and Z coordinates. Vertices are the points where edges and faces meet. The plural is vertices.
WAG FILE:: A simulator configuration file for a wagon or non-powered vehicle. It defines physical details such as braking, couplers, and other properties.

You should also describe the intended compatibility of your finished content in its README file.
(((Content Design, "Choices")))

Made for {MSTS}:: The content can run in Open Rails, but it may need WAG or ENG edits because some legacy {MSTS} physics values may not perform well in {OR}.
Made for ORTS - No other files required:: The content is configured for {OR} and requires no additional files.
Made for ORTS - but requires other add-ons:: The content is configured for {OR}, but needs other downloaded files to work. NAVS-based items are a common example.
Made for ORTS but Compatible with {MSTS}:: The content is built for {OR} but also configured to remain compatible with {MSTS}. This usually takes more work.
Made for ORTS but requires {MSTS}:: The content runs in {OR}, remains compatible with {MSTS}, and also requires files from a local {MSTS} installation.
Made for ORTS but requires {MSTS} and other add-ons:: The content is configured for {OR}, but also requires a local {MSTS} installation and other default or add-on files.

Choose the option that best matches your goals. Consider these questions:

* How familiar are you with Open Rails and its content options?
* How much effort do you want to put into this project?
* How much 3D modeling experience do you already have in tools such as Train Sim Modeler, GMAX, or 3D Canvas?
* How much Blender experience do you have?
* How much experience do you have creating content for Open Rails compared with {MSTS}?
* How flexible does your content need to be?

== Content Generation

Creating Open Rails content usually requires several related pieces. The list below is not complete, but it gives the basic shape of a simple train-related model project.

(((Blender, "Getting Started")))

* A mesh, which is the 3D model.
* Reference material and online resources. TrainSim.com and Elvas Tower are useful starting points: https://www.trainsim.com/vbts/forum.php and http://www.elvastower.com/forums/index.php
* A texture, also called a skin: a 2D bitmap image applied to the model.
* A UV map: the mapping that tells Blender how the 2D texture fits onto the 3D mesh. Blender can create UV maps, although tools such as UVLayout or Substance Painter can also be used.
* Configuration files that describe the content to the simulator. For rolling stock, these are usually WAG or ENG files.
* A thumbnail JPG. This is optional, but useful.
* Instructions. Do not leave the project half documented.

=== Programs you should have

* A 3D program. {version} is recommended. The current release, {BV}, should also be fine unless Blender's Python API has changed enough to affect the exporter add-on. Blender 5.0 is an example where exporter updates may be required.
* An exporter add-on for the {MSTS}/ORTS format. This notebook uses Wayne Campbell's _S File Exporter_ from Elvas Tower. footnote:[Download from https://github.com/pwillard/Blender_{MSTS}_ORTS_Exporter]
* A paint program with layers and channels.
* A text editor that handles Unicode files.

NOTE: If you also make models for Trainz Simulator, current Trainz versions can use files exported by Blender's built-in FBX exporter.

=== What the author uses

* 3D modeler: {bv}
* Bitmap tools: Canva, Affinity Studio, or Paint.NET
* UV/shader tools: Blender's built-in tools. Third-party tools such as Substance Painter exist, but I do not use them for this workflow.
* Text editor: _Microsoft Visual Studio Code_
* Metric conversion calculator: a hand-held calculator or Google
* Scale calculator: useful for converting dimensions from scale drawings. One is available at http://www.railsimstuff.com

[NOTE]
Use metric measurements when possible. Metric is the default in Blender and {OR}. U.S. customary units may be familiar, but metric is better for worldwide compatibility and is usually simpler once you stay with it.

== Why Many Other People Use Blender to Make Content

Blender is a powerful, flexible, free, and open-source 3D application. It is widely used for game and simulator assets for several reasons.

Open-Source and Free:: Blender is free to use and has an active community of developers and users. It is accessible to hobbyists, indie developers, and professionals.
Versatility:: Blender includes tools for modeling, sculpting, texturing, rigging, animation, rendering, and more. It can create characters, environments, props, vehicles, and effects.
Integrated Workflow:: Modeling, editing, UV mapping, animation, and rendering can all happen in one application. This reduces the need to move between separate tools.
Asset Optimization:: Blender includes tools for LODs, texture baking, and UV map management, all of which help prepare assets for real-time rendering.
Community and Resources:: Blender has a large user community with many tutorials, forums, and training resources.
Non-Destructive Workflow:: Modifiers and procedural workflows allow changes without immediately destroying the original model data.
Constant Development:: Blender is updated often. New features and improvements arrive regularly, sometimes faster than users can keep up with.

Blender is not the only possible tool, but it is a strong choice if you want a free, capable, and actively developed modeling package.

To export a model for {MSTS} or {OR}, use Wayne Campbell's Blender MSTS/Open Rails exporter add-on for {MSTS}-format `.s` files.

===== Installing Add-Ons with Version 4.x

Blender add-ons expand Blender with tools, import/export features, UI panels, and automation. Add-ons may be bundled with Blender, downloaded by Blender, or installed from third-party ZIP packages.

===== Enabling Built-In Add-ons

. Open *Edit → Preferences…*
. Select the *Add-ons* tab.
. Search for the add-on.
. Enable it with the checkbox beside its name.

NOTE: Some bundled add-ons may require a small download the first time they are enabled.

===== Installing Third-Party Add-ons

. Download the add-on as a `.zip` file.
. In Blender, open *Edit → Preferences → Add-ons*.
. Click *Install…* in the upper right.
. Select the ZIP file and click *Install Add-on*.
. Enable the add-on with its checkbox.

TIP: Do not extract the ZIP unless the add-on's instructions tell you to. A Blender-installable ZIP normally contains an `__init__.py` file at its root.

==== After Installation

Add-ons may:

* Add panels to the Sidebar, opened with kbd:[N].
* Add menu items under *File → Import* or *File → Export*.
* Add settings in the add-on's Preferences section.

If *Auto Save Preferences* is enabled, Blender remembers enabled add-ons the next time it starts.

==== Also in Blender 4.x - Extensions

image::images/editors_preferences_section_extensions.png[align=center]

Blender 4.x introduced the Extensions system. Extensions include add-ons, themes, keymaps, and other modular packages. They are managed through Blender's extension tools and the official Blender Extensions Platform at extensions.blender.org.

Extensions are meant to make finding, installing, enabling, updating, and removing modular features easier from inside Blender.

[NOTE]
The term "Add-ons" is still valid. Newer Blender versions use "Extensions" to cover more than Python add-ons.

To enable the feature the first time:

* Open *Edit → Preferences* and go to the *Extensions* or *Get Extensions* tab.
* If prompted, allow Online Access.
* Blender will show available extensions from the official platform.

To browse for extensions:

* Click *Get More Extensions* at the bottom of the Extensions tab.
* Blender opens the Extensions Platform website in your browser.
* Search by name, category, or author.

To install, enable, update, or uninstall extensions:

* Click *Install* beside the extension you want.
* Use the checkbox to enable or disable it.
* Click *Update* when an update is available.
* Click *Uninstall* to remove it.

== Content Creation Overview

The next sections are not just about Blender modeling. They describe how to create items that meet simulator requirements and conventions. Some older 3D Crafter notes are included where useful.

=== Orientation
((( Content Creation, "Orientation")))

Rolling stock and engines must be oriented correctly. In some older 3D programs, such as 3D Crafter / 3D Canvas or Maya, Z may represent depth, X width, and Y height. Blender is closer to 3ds Max: Z is height, X is width, and Y is depth.

For track vehicles, the front of the model points toward positive Y. The rear points toward negative Y.

[WARNING]
Blender's default front view is different. Blender considers the front to face the -Y direction. Pressing kbd:[1] on the keypad shows Blender's front view, which is the back end from the {MSTS}/{OR} perspective.

=== Engine/Wagon Model Hierarchy

(((Content Creation, "Engine/Wagon Model Hierarchy")))

The Blender exporter requires a collection named `MAIN`. This is the root of the model hierarchy. The model itself is not placed directly in `MAIN`; instead, model parts are placed in child LOD collections such as `MAIN_700` and `MAIN_2000`.

image::images/layout-h.png[]

[WARNING]
The Blender exporter expects required collection names to be capitalized, such as `MAIN`, `MAIN_700`, `BOGIE`, and `WHEEL`. Names such as `main` or `main_700` will cause export errors.

For {OR} to animate wheels and bogies correctly, the model hierarchy, names, parenting, and pivot origins must be correct. In the following example, the A-end of the boxcar is on the right, the B-end with brakes is on the left, and default travel is from left to right. See the Orientation section above.

image::images/heir.png[]

[TIP]
For a two-bogie, two-axle arrangement, each wheel object should use the center of its axle as its pivot. Each bogie should use its own center of mass as its pivot. Most other parts use world origin as their pivot.

[NOTE]
The main body mesh does not need to be named `MAIN`. Modelers have used that name by convention since 2002, but the exporter only requires the `MAIN` collection to exist.

[WARNING]
Be careful when selecting all objects and applying all transformations. This can reset all object origins to world origin, which would break bogie and wheel pivot points.

=== Standard 2 Axle Freight Bogies
(((Content Creation, "Standard 2 Axle Freight Bogies")))

From the left-side view, the model faces right. Starting from the right side, name bogies and wheels according to the hierarchy diagram. The correct wheels must be parented to `BOGIE1` or `BOGIE2`.

For an extra axle, use `WHEELS13` or `WHEELS23` behind the bogie pivot relative to forward motion, and shift wheel set 2 to the center of that bogie. Keep the naming sequence from 11 through 23 as shown. Incorrect order can cause wheels to rotate backward or shift incorrectly in {MSTS}.

[NOTE]
A two-axle bogie would not use `WHEELS13` or `WHEELS23`.

=== Isolated Axles

The {MSTS} naming standard for isolated, non-bogie axles is `WHEEL1`, `WHEEL2`, `WHEEL3`, and so on.

NOTE: These are mainly used for steam locomotives. Their animation is not automatic and must be created in Blender. Steam wheel and linkage animation uses 16 frames and should be treated as an advanced topic.

In {OR}, the important parts appear to be the `WHEEL` and `BOGIE` prefixes. `WHEEL` is required for wheel animation and proper bogie parenting. `BOGIE` is required for bogie animation and proper engine or wagon parenting.

[WARNING]
Some {MSTS} documentation implies that a third bogie is possible in {MSTS}. It is not. If you are modeling specifically for {OR}, the simulator can animate correctly named bogie and wheel objects as long as parenting and local pivot origins are correct.

=== Include Files in Configurations
(((Configuration, "Include")))

`Include()` statements are becoming more common in {OR} SIMIS files, but includes are optional.

In both {MSTS} and {OR}, `.wag` and `.eng` files identify an asset as a locomotive or non-powered vehicle. Historically, these files were large, complicated, and full of repeated data. MSTS files usually had to be self-contained. In {OR}, `.wag` and `.eng` files can include shared `.inc` files, which makes the main files smaller and easier to maintain.

Include files are especially useful when creating several similar cars that differ only in details such as reporting marks.

An `.inc` file does not have to be in the same directory as the `.wag` or `.eng` file, although that is sometimes easiest. It only needs to be referenced in a way {OR} can find.

[WARNING]
When `.inc` files are used by `.eng` or `.wag` files, they need a blank line at the beginning. For safety, also leave a blank line at the end.

When ORTS loads a locomotive or car, it reads the main `.eng` or `.wag` file until it reaches an `Include` statement. It then locates and reads the `.inc` file, inserts that data into the physics data, and returns to the main file. It repeats this process for additional include statements.

*Common include-file locations:*

* A subfolder inside the `.wag` or `.eng` folder.
* Directly in the `.wag` or `.eng` folder. This can become messy, so use caution.
* A special folder for files shared by `.wag` or `.eng` files that use the same `.s` shape.
* A common folder shared by many `.wag` or `.eng` files.

Create a naming standard that supports both common shared files and files specific to a master shape.

==== General INC file structure

(((Configuration, "Include, Structure")))

INC files are still standard {OR} configuration documents, so SIMIS rules still apply. Keep these points in mind:

* The first line of the INC file must be blank.
* Do not include a SIMIS header line such as `SIMISA@@@@@@@@@@JINX0D0t______`.
* Use `COMMENT()` sections generously.
* INC files are most useful for shared configuration values.
* INC files are for {OR} only. MSTS cannot use them.
* {OR} reads include files from top to bottom. If values are duplicated, the last value read overrides earlier ones.

==== Items well suited to INC files

* Coupler details shared by many locomotives or cars.
* Wagon details shared by many locomotives or cars, such as sound references and empty/loaded states.
* Brake details shared by many locomotives or cars.
* Lights shared by similar vehicles.
* Davis coefficients shared by similar vehicles.

Use includes thoughtfully. They can simplify a project, but they can also become complicated quickly.

==== Specifying relative references

(((Configuration, "relative reference")))

{OR} must be able to locate your INC files. Use references that are relative to the main file whenever possible.

* If the INC file is in the same folder, use `INCLUDE("filename.inc")`.
* If it is in a subfolder, use `INCLUDE("subfolder/filename.inc")`.
* If it is elsewhere, use an absolute path such as `INCLUDE("C:/path/to/filename.inc")`, or a relative path such as `..\common.inc\filename.inc` to refer to a common folder one level up.

[NOTE]
There is a way to keep content compatible with legacy MSTS while using this technique, but it is not covered here.

_An interesting discussion occurred in 2017 about making these files better and more useful in the post-Microsoft Train Simulator world._

[quote, Erick Cantu, 20 November 2017]
_____
KUJU defined many of the folder names used in {MSTS}. The Include file concept for `.eng` and `.wag` files led me to think that something like KUJU's `\common.cab` directory tree was needed for `.inc` files.

Payware vendors used several folder approaches under `\trains`: sometimes `\common.cab`, sometimes a product-specific folder, and sometimes a vendor folder for an unskinned mesh, such as `3DTrains_FPack`.

The KUJU CAB file provides a useful example for locating include files. After experimentation, I propose a solution that addresses these needs:

* A shared folder for `.inc` files, much like `\common.cab`.
* Recognition that users may have routes and equipment from many countries, so grouping certain files by country may be useful.
* Acceptance that payware vendors may sell the same mesh in many railroad skins while distributing each railroad in a unique folder.
* A simple approach for cases with minimal commonality, where everything belongs in one folder.
_____

=== Config File Deconstruction

(((Configuration, "Deconstruction")))

A configuration file has two basic parts:

* Header: the first line, identifying the file type and version.
* Body: the actual configuration data.

==== Header

The first line is always the header. It begins with `SIMISA@@@@@@@@@@JINX0D0t______` and is followed by a blank line. It identifies the file type and version; it is not part of the vehicle data. Different file types can use different header lines.

[source,text]
----
SIMISA@@@@@@@@@@JINX0D0t______

----

The body contains the configuration data.

=== General Modelling Standards from Erick Cantu
(((General Modeling Standards, continued)))

These notes from Erick Cantu are important enough to preserve as a reference. They were extracted from Elvas Tower forum posts and are useful if you want to model with similar standards. They are guidelines, not hard rules.

[WARNING]
Erick gives detailed modeling guidance here. Read and keep these points in mind when planning your own models.

==== Erick Says

* Match the right trucks to the right car. This includes wheel size and truck wheelbase, not just broad truck type. Erick built a library of freight-car trucks for this reason. His truck library is available at Elvas Tower, and importing those trucks into Blender could be very useful.
* Map standard-definition cars at about 1/2 inch per pixel. Align adjoining car surfaces within 1/1000 of a pixel so continuous lines do not break. Map car sides separately. Many cars can use the top or bottom half of a 2048 x 2048 sheet, which creates large continuous surfaces and lets one sheet support two paint schemes.
* A useful setup is four shape files: two mapped to the top and bottom of the first texture sheet, and two mapped to the top and bottom of the second. This supports four paint or weathering patterns per car folder, while numbers can be applied with decals so one shape can represent many cars.
* Texture mapping should be intuitive and paintable. Ask: Would I want to paint this? Could I repaint it for another railroad? Can unneeded parts be hidden with alpha? Could I paint it without constantly checking in Shape Viewer? Avoid awkward angled mappings that make straight lines difficult.
* Use consistent bitmap resolution and mesh resolution across a car and across related parts. Ideally, the top LOD should stay near 12,000 triangles or less, with careful vertex optimization, limited hard edges, and welded UV coordinates where possible.
* Aim for one texture sheet for the car body and one for the trucks. If alpha is needed, the whole car body can often use one BlendATexDiff material with the -Trans flag off. Add extra materials only for a clear reason, because each material adds a draw call. Trucks can use a separate texture because animated parts already create a separate draw call.
* Texture resolution and mesh resolution should match the intended viewing distance. Do not build highly detailed parts with high-resolution textures on a low-resolution model. Detail that greatly exceeds the rest of the model wastes texture space and vertices. There are exceptions, such as number boards with alpha edges, where higher texture resolution may be needed for acceptable results.
* Avoid splitting car sides into multiple sections unless necessary. It adds mesh divisions and UV coordinates. Very long cars may require it, but cars around 60 feet or less usually do not if planned well. Multiple car bodies can share one texture sheet, and this can reduce total train texture counts.
* Place the top node's pivot about 2 inches below the rail so the wheels sit correctly. You may still need to adjust ride height.
* Consistent detail helps cars look good together. Air hose heights should match across cars. Erick uses brake hose ends at 14.5 inches above the rail and extends them to meet the next car's hose, held as in the real world with a chain or cable.
* Couplers passing through other couplers look bad. It is often best to make couplers part of the truck mesh or link them to the trucks. Exceptions include cars where truck centers and couplers are far apart, such as auto-racks or cushioned boxcars.
* Keep draw-call counts low and texture counts even lower. A car body should use one texture sheet and one material unless another material is truly needed. Multiple car bodies can share a single square sheet if needed.
* Avoid unnecessary 1-bit alpha and aliased edges. OR handles 32-bit textures correctly, so separate materials for 1-bit and 8-bit alpha often just add draw calls. Use one material with 8-bit alpha where possible. A 1-bit alpha channel is acceptable only for perfectly square transparent areas.
* Do not leave freight-car undersides empty. The old {MSTS} habit of leaving the underside open can show sky through the car when viewed from below, especially on bridges. The underside does not need to be complex, but it should exist.
* Use the units that match your references. Aircraft references may be in decimal inches or meters. U.S. rolling stock references are often in inches. A scale calculator makes conversion manageable, and you may grow to like metric.
* Do not add imagined details. Model as accurately as practical.
* Within your target viewing distance, model visible details at a resolution consistent with the rest of the model. Brake rigging can be complete but simple if the car is normally viewed from far enough away that the whole car is visible.
* Taper wheel treads. It is obvious when they are not tapered.
* Weld UV coordinates wherever possible. Texture vertices matter as much as draw calls.
* Plan hard edges deliberately. If an edge is always in a dark area, smoothing it may be better.
* Cars should look good from all likely viewing angles, including below.
* Blender can export a UV image. Import this image into your paint program as a reference layer so you can see where texture shapes are located.
* Smaller round parts need fewer sides. Wheels may use 24 sides at the rims, but 12 or 10 sides inside the dish. Edges matter, but they can hide a lot.
* Coupler heights may vary. Air hose heights should not. Consistent hose height prevents mismatches between cars.
* If a feature cannot be done well, leave it out. For example, track sounds for switches and crossings can break immersion if they cannot account for truck spacing or wheel count.

The main point is to make deliberate choices. Small inefficiencies add up across a long train, especially with AI traffic. Erick's move from individual car textures to shared paint and weathering variations with decal numbers reduced texture counts dramatically. For example, 100 BN hoppers can use 13 texture sheets with decals, instead of about 51 sheets without them.

=== Additional guidance from Blender Brothers

From Pete Willard:: Josh from Blender Brothers was one of my mentors when I was learning Blender. I subscribed to their YouTube channel and still receive updates about their ideas and tips.

Josh and Ryuu of Blender Brothers say:

"What's the secret to nailing the detailing stage?":: It comes down to understanding where to add detail, how much to add, and what kind of detail fits. That sounds simple, but it takes practice.

==== Blender Brother's Gold Rule

Think in terms of visual anchors. Visual anchors are like stars in a constellation. Your eye moves from one anchor to another, while the space between them becomes negative space. These tips help apply that idea:

* *Embrace the 70/30 Rule* Keep about 70% of the design clean and cluster details in the remaining 30%. This creates visual anchors.
* *Keep Details to scale* Oversized details can make a model look cartoonish. Use reference scale when needed.
* *Do your homework* Use reference images. For example, study real or fictional examples before designing a sci-fi room.
* *Less is more* Do not over-detail one area all at once. Move from area to area and add detail gradually.
* *Create your own library* Build a collection of decals, trim sheets, kitbash parts, and other reusable assets. This speeds up work and keeps your style consistent.

=== General Texture Mapping Guidelines

* Microsoft recommended square texture sizes for {MSTS}, such as 512 x 512, 256 x 256, and 128 x 128. {OR} does not have the same limitation, so a 2048 x 1024 texture can be reasonable.
* Use a paint program that supports layers and can save layered documents. PSD is one layered format.
* PNG files support alpha channels, but they do not preserve layers.
* Consider using PNG files while modeling and DDS files for final {OR} models.
* Consider using modeled decals for reporting marks and car numbers instead of baking them into the main texture. Decals are easier to change and can be reused on multiple models.
* Export and check the model as soon as the UV map exists. It is better to find UV problems early.

* ORZIP:: A free tool that replaces Microsoft Train Simulator's ffeditc_unicode.exe file for compression and decompression of MSTS files. It is available at https://github.com/pwillard/orzip/releases  NOTE: ORSP is a graphical front-end for ORZIP that is also available at https://github.com/pwillard/ORSP/releases
* TextureWorkshop:: A free tool for converting ACE files into multiple other formats. It is available at https://github.com/pwillard/TextureWorkshop/releases
* REPMARK:: Generate transparent PNG decal sheets for railroad reporting marks and numbers. It is available at https://github.com/pwillard/repmark/releases
* Shape Conversion:: A free tool for converting MSTS shape files into Blender-readable formats. It is available at https://github.com/pwillard/ShapeConversion/releases
